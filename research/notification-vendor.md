# Notifications: build it ourselves or use a vendor, and which vendor

Research for [#3](https://github.com/noelhuang/cohort-005-project-2/issues/3), part of the map [#2](https://github.com/noelhuang/cohort-005-project-2/issues/2). Researched 2026-11-16 against vendor docs, pricing pages and the npm registry. Vendor pricing and plan gates change often, so recheck the cited pages before committing money.

## Recommendation

**Build it ourselves on SQLite (Drizzle) and Postmark.** Keep the vendor seam narrow, so that moving to **Knock** later stays cheap if the feed or workflow needs outgrow us.

Why:

1. **The hardest trigger is ours either way.** An inactivity nudge depends on `lesson_progress` and `video_watch_events`, which live in our SQLite file. No vendor can see that data. With every vendor we would still run our own scheduled job that finds inactive Students and calls the vendor. Knock's schedules fire on a timer, not on activity ([Knock schedules](https://docs.knock.app/concepts/schedules)). MagicBell says its API trigger suits "scheduled jobs" you run yourself ([MagicBell workflows](https://www.magicbell.com/workflows)). The vendor would only save us the template and send step.
2. **Our scale is small, and a vendor's free tier gives the least where we need it most.** Novu Free caps delay and digest windows at 1 day ([delay](https://docs.novu.co/platform/workflow/add-and-configure-steps/configure-action-steps/delay), [digest](https://docs.novu.co/platform/workflow/add-and-configure-steps/configure-action-steps/digest)). Knock's next tier after Free costs $250/month ([Knock pricing](https://knock.app/pricing)). MagicBell's is $249/month, and its Free plan has 1,000 deliveries ([MagicBell pricing](https://www.magicbell.com/pricing)).
3. **Tests and DevUI get simpler.** A table of our own works offline in vitest and needs no auth step: the feed loader reads `notifications WHERE user_id = session user`, so a DevUI user switch just works. A vendor feed needs a server-signed token for each user, and that token must be reissued on every DevUI switch (see below). None of the vendors offers an offline emulator.
4. **Personal data stays with us.** We record the buyer's country. Knock has no EU data residency yet ("expected by the end of 2026", [Knock plans](https://docs.knock.app/manage-your-account/knock-plans)). Courier's EU region is provisioned case by case ([Courier security](https://www.courier.com/docs/workspaces/security#regions-and-data-residency)). MagicBell publishes no hosting region. A vendor would hold names, emails, roles and Comment or Question excerpts.

What we take on (the trade-offs):

- **Feed UI.** We build a bell, an unread badge and a list with Radix and shadcn, which are already dependencies. There is no real-time push: we poll or revalidate on navigation. Knock, Novu and Courier ship WebSocket-backed components.
- **A job runner.** The app has none today (no cron, no queue). Digests, batching windows and nudges need one, for example a `notification_jobs` table and a small worker or cron script that runs every few minutes. This is the largest new piece of infrastructure.
- **Batching and digests.** We write the window logic ourselves: group pending deliveries by (recipient, key) and send once when the window closes.
- **Preferences and unsubscribe.** We need a preferences table with a row per (category, channel), a "required" flag for refund emails, signed unsubscribe URLs, and the `List-Unsubscribe` and `List-Unsubscribe-Post` headers. Google requires one-click unsubscribe for marketing and subscribed mail from senders above 5,000 messages a day ([Google sender guidelines](https://support.google.com/a/answer/81126)). We are below that, but it is cheap to do from the start.
- **Postmark streams.** Inactivity nudges and digests are closer to "broadcast" than "transactional" under Postmark's rules: "if multiple recipients get the same content and it isn't triggered by an event, it isn't transactional", and bulk mail must not go through transactional streams ([Postmark: what are transactional emails](https://postmarkapp.com/support/article/804-what-are-transactional-emails), [unsubscribe links](https://postmarkapp.com/support/article/1208-how-to-add-an-unsubscribe-link)). Plan for two streams: `outbound` for event Notifications and refunds, and a Broadcast stream for nudges and digests. This applies whichever option we choose.
- **Delivery history.** Delivery logs, retries and bounce handling become our code. Postmark webhooks give us bounces.

**When to revisit:** pick Knock if we need real-time feed updates, many more workflow types, or non-engineers editing templates. It is the best fit on paper: React 19 peers, the strongest Postmark integration, batching, schedules, preferences with commercial versus required semantics, and sandbox mode. Its blockers are EU residency and the $250/month tier above 10,000 messages.

For every vendor, the data that must be sent is: user id, name, email, role (for targeting), timezone (for schedules), and each Notification's payload. That payload includes Course titles and Comment or Question excerpts if the email or feed shows them.

## Ranking if we do pick a vendor

1. **Knock.** It has the most complete feature set for this spec and the cleanest React 19 story. Its auth model lets dev run without signed tokens. Weak points: no EU region yet, and a steep step from Free to $250.
2. **Novu.** It has EU residency on Free and a cheap Pro tier ($30). It also has a "critical workflow" concept that matches refund emails. Weak points: on Free, delay and digest windows are capped at 1 day and retention at 24h, so a weekly digest needs Team. Self-hosting is heavy (MongoDB + Redis + 4 services) and gives no offline test story.
3. **Courier.** Its `REQUIRED` topics fit the "cannot opt out" rule. Weak points: every send is billed on Business, and the docs and pricing page disagree on whether digests are Enterprise-only.
4. **MagicBell.** Its Free tier is small (1,000 deliveries), we found no documented digests or scheduling, and it publishes no data region.

## Facts about this repo that differ from the brief

- **There is no Postmark mailer and no `.outbox/` fallback in the repo today.** `app/lib/mailer.server.ts` does not exist on `main` or on any local branch. On the `approve-decline-refund-requests` branch, `app/lib/refunds.server.ts` builds `RefundEmail` objects and only `console.log`s them (`logEmails`). Whichever option we choose, the mailer and its offline fallback still have to be written, and the map's "Existing email infrastructure" note should be corrected.
- The app runs **React Router 8.3.0** (from `package.json`), not 7, with React 19.2.
- There is no background job or cron infrastructure in `app/`.

## Unverified or possibly outdated

- Knock: delay step details and plan gating for delays and schedules are not on the pricing page. The EU residency date is a roadmap statement.
- Novu: per-plan availability of the Inbox and preferences was not readable from the pricing page. Self-host licensing and feature gaps link to a comparison page we did not read.
- MagicBell: digests, preferences "required" semantics, data region and workflow GA status were not found in the docs.
